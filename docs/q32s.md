# Q32S firmware analysis

2026-10-23. Target: the official application now installed on the Gamebrick. SHA256 `2fb44f4235bd4ed7183439f31ee2a31fb0052d19dd736e20d1d251fd5e1ff259`, 198,824 bytes, load address `0x01e00120`. This is a partial reverse engineering with live protocol verification, not recovered source suitable for rebuilding.

## Verified results

The USB vendor interface responds to B4/B5 framing. Nine MessagePack GET commands succeeded: info, keyboard, mouse, consumer controls, touch, XInput, DInput, sleep and screen. The controller returned `mode_name: mt_IINE`, `version: 0x0300`, protocol version `1`, transport `8`, MTU `64`. These are firmware response fields; `mode_name` is not proof of the active Bluetooth advertising mode.

Evidence:

- [Address map, GATT records and decoded settings](evidence/q32s-stock-analysis.json)
- [Raw identification requests/replies](evidence/stock-usb-queries.jsonl)
- [Raw configuration requests/replies](evidence/stock-usb-settings.jsonl)

All operations in this analysis were reads or offline work. No firmware or configuration writes were performed. USB command responses do not establish that pairing, all physical buttons or iOS background operation work.

## Memory and report path

Startup copies application data at file offset `0x2dea8` to RAM `0x840` (length `0xc60`), and code/data at `0x2eb08` to RAM `0x40c0` (length `0x1d88`). Disassembling the latter at its flash storage address gives wrong branch targets.

| Address | Role | Evidence |
| --- | --- | --- |
| `0x00004c62` | Transport transmit router in RAM | Calls HID and vendor send paths |
| `0x00004d10` | HID call inside router | Calls `0x01e0420c`; strips report ID from byte 0 |
| `0x00004dc2` | Vendor call inside router | Calls `0x01e06180` |
| `0x01e0420c` | `ble_hid_data_send(id, data, len)` | Checks IDs 1–6, reads handle table, sends ATT |
| `0x01e04250` | AE42 sender | ATT handle `0x54`, connection at RAM `0x29e2` |
| `0x01e034b4` | ATT send wrapper | Rejects missing connection; dispatches command `0x1a` |
| `0x01e041ba` | Report subscription readiness | Checks HID CCCs or vendor CCC `0x55` |
| `0x01e04c84` | ATT write callback | AE41 handle `0x52` enters vendor receive handling |
| `0x01e06180` | Vendor transmit adapter | Routes transport values 0/4 to AE42 |
| `0x01e064ce` | Command frame transmitter | B4 fragmentation; checksum only for transport 10 |
| `0x01e09f3e` | Frame receiver/reassembler | B4/B5 checks and fragment state |
| `0x01e075e6` | Command dispatcher | Standard opcodes and MessagePack command `0xcc` |
| `0x01e0c122` | Keyboard report sender | Report ID 2 plus keyboard payload |
| `0x01e0ce10` | Large report-processing routine | GPIO scanner/debounce recovered; consumer/remapping paths remain partial |

The RAM router calls the HID sender only after readiness/state checks, including `(RAM[0x2d14] & 6) == 6` and `RAM32[0x2d1c] == 4`. **The earlier patch at the HID sender may therefore miss input when only the vendor service is in use.** A vendor-only connection must be tested before treating that prototype as a solution. Capture the report or logical key state before the HID readiness checks; gate vendor transmission on its own CCC state.

The current candidate also omits report ID, so different HID payload types cannot reliably be distinguished. Use explicit report ID framing or a documented six-button state report, including releases and backpressure handling. No revised patch was flashed.

## GATT profile

The full profile begins at `0x01e220be` and contains 91 records. A separate one-service table exists at `0x01e21fb4`.

| Service | Write characteristic / handle | Notify characteristic / handle | CCC |
| --- | --- | --- | --- |
| AE40 | AE41 / `0x52` | AE42 / `0x54` | `0x55` |
| AE00 | AE01 / `0x82` | AE02 / `0x84` | `0x85` |

HID report IDs 1–6 map to value handles `0x27`, `0x2b`, `0x32`, `0x36`, `0x3a`, `0x3e`. Their CCCs are the next handle. The write callback sends the observed `ff` on AE02 after its CCC is written; that byte is not a button report.

The vendor command path exists over BLE in the binary, but this session verified the protocol over USB only.

## Vendor protocol

USB reports are 64 bytes, padded with zeros. hidapi writes require a leading report-ID byte `00` that is not part of the vendor frame.

- Short request: `B5 length command payload...`.
- Response/fragment: `B4 length sequence command payload...`.
- `length` counts frame bytes, excluding USB padding and hidapi's report-ID prefix.
- Sequence bit 7 starts a message; bits 0–6 count remaining fragments, including the current one. A single response uses `81`.
- USB/BLE do not append a checksum in this firmware. The serial transport (10) has an additive checksum.
- Command `CC` carries MessagePack. Put `cmd` first: the dispatcher initially reads a map and expects that first key. These queries then supply `key: all`.

Verified request:

```text
B5 19 CC 82 A3 63 6D 64 A8 67 65 74 5F 69 6E 66 6F A3 6B 65 79 A3 61 6C 6C
```

Payload: `{"cmd":"get_info","key":"all"}`. Reply: `{"cmd":"ret_info","mode_name":"mt_IINE","version":768}`.

The MessagePack parser matches the structure/type dispatch of [cmp](https://github.com/camgunz/cmp/tree/e564b7a06bd39e7ab2f19f9a616a3d268638a88d). The framing/reassembly matches the pinned LiteEMF source with OEM differences: B4/B5 headers and transport-specific checksum handling. Do not use upstream A4/A5 defaults.

Static SET branches include `set_kb`, `set_mouse`, `set_cs`, `set_mt`, `set_xinput`, `set_dinput`, `set_sleep`, `set_screen`, `set_restore`. None was sent. No existing command that enables unsolicited BLE button reports has been established. Opcode `0x12` has a special USB-only branch; its live behavior remains untested.

## Recovered mappings

These are configuration values, not a new physical-button capture.

| Logical key | Keyboard usage bytes | Mouse mapping |
| --- | --- | --- |
| `0x00` | `28 00` | Button 1 |
| `0x01` | `2c 00` | Button 2 |
| `0x10` | `52 00` | Y −2 |
| `0x11` | `51 00` | Y +2 |
| `0x12` | `50 00` | X −2 |
| `0x13` | `4f 00` | X +2 |

The directional values identify Up/Down/Left/Right respectively. Confirm which face button is logical 0/1 with a physical capture. Keyboard values arrive as MessagePack extension type 0, three bytes; the third byte's meaning is unresolved and preserved in the evidence.

XInput and DInput getters returned empty maps; that does not mean those modes lack button support. Consumer mappings include a `0x14` key and omit `0x01`; retain the actual result until tested. Sleep values are `discon:10, con:15`; units are not established. Screen settings are iOS 393×852, Android 1080×2560, with raw `ios_ver:0x0f00`.

## Tools and reproduction

REA rejects raw Q32S. Ghidra 12.2 with the pinned Jieli processor module imports this firmware. Local project:

```text
research/q32s-analysis/gamebrick-<timestamp>.gpr
research/q32s-analysis/corrected/decompiled.c
research/q32s-analysis/corrected/listing.txt
research/q32s-analysis/corrected/functions.tsv
```

`prepare-q32s.py` creates an isolated processor copy. It corrects three `jls` constructors (`<=`), three `jge` constructors (signed `>=`), and normalizes long branch destinations to 25 bits. ROM calls then match `maskrom_stubs.ld`, and RAM calls resolve back to the HID/vendor functions. The pinned upstream source remains unchanged.

The extended processor now decodes all 85 previous constructor failures and supplies register-list stack semantics; see [decoder results and remaining limits](q32s-decoder.md). Generated C can have wrong types, arguments or missing paths; check assembly and live evidence. Function discovery is heuristic, and exports include library code and possible false positives. This is not a complete decompilation. The recovered GPIO scanner and a compiled AE42 component are described in [custom-firmware.md](custom-firmware.md).

The official Ghidra zip is retained in `.tools/ghidra/release.zip`; its URL and checksum are in the tool evidence. Extract it under `.tools/ghidra`, copy `research/ghidra-jieli` to `Ghidra/Processors/JieLi`, and use JDK 25 or later. The release lacks the Mac decompiler binary. Build it in `Ghidra/Features/Decompiler/src/decompile/cpp`:

```sh
make -j6 ghidra_opt ARCH_TYPE='-arch arm64' ADDITIONAL_FLAGS='-mmacosx-version-min=14.0' OSDIR=mac_arm_64
mkdir -p ../../../os/mac_arm_64
cp ghidra_opt ../../../os/mac_arm_64/decompile
```

From the repository root:

```sh
./scripts/analyze-q32s.sh
.venv/bin/python research/test_stock_protocol.py -v
.venv/bin/python research/query-stock.py            # preview packets
.venv/bin/python research/query-stock.py --usb      # read identification
.venv/bin/python research/read-stock-settings.py    # read nine settings groups
```

Five regression checks pass: live reply replay, GET allowlist, malformed fragment rejection, malformed MessagePack rejection, and ROM/RAM branch targets. Full-flash installation verification remains documented separately in [stock-update.md](stock-update.md).
